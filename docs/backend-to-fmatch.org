#+TITLE: Backend -> fmatch: how the request is sent and with which parameters
#+AUTHOR: Pay3Flow
#+DATE: 2026-09-17

* Purpose

The backend (=backend= folder) consumes fmatch as an *external read-only service*:
it pushes a payment task into fmatch's inbox and reads the ranked candidate list
back. Nothing inside fmatch is edited. This document describes what exactly the
backend sends, where, with which HTTP headers, and with which parameters in the
body.

Related code:
- =backend/src/quotes/mod.rs= -- content rendering + quote computation;
- =backend/src/activitypub/service.rs= -- building the Proposal and sending it;
- =backend/src/activitypub/model.rs= -- activity shape and response parsing;
- =backend/src/activitypub/delivery.rs= -- HTTP delivery, signing, retries;
- =backend/src/activitypub/signature.rs= -- HTTP Signature (rsa-sha256);
- =backend/src/config.rs= -- fmatch settings.

* Overall flow

#+begin_src text
  Client (REST / WS)          backend                        fmatch:7277
        |                     |                               |
  POST /api/debug/quote       |  1. fmatch_content(req)      |
  GET  /ws/rates              |     -> content string        |
  POST /payments/*            |                               |
        |---------------------+--2. request_proposal():      |
                              |     Proposal(purpose="request",
                              |     command="candidates",
                              |     content=..., resultInbox=..)
                              |--3. POST /inbox/actra ------->| filter solver pool
                              |     with HTTP signature     |  by content
                              |<---- Offer/candidates --------| (inline list)
                              |--4. AcquirerCandidate::from_reply
                              |     -> Quote{source,candidates,best}
#+end_src

If fmatch is unreachable (timeout / network error / 5xx after retries),
=compute_quote= does not fail; it switches to the local rules-based fallback
(=routing/matcher.rs=) and =Quote.source= becomes =fallback=.

* fmatch configuration (backend/src/config.rs)

| Variable              | Default                              | Meaning                             |
|-----------------------+--------------------------------------+-------------------------------------|
| =FMATCH_INBOX=        | =http://localhost:7277/inbox/actra=  | inbox URL the POST goes to          |
| =FMATCH_ACTOR_ID=     | =http://localhost:7277/actor/actra=  | fmatch actor IRI (Follow/reply)     |
| =AP_ORIGIN=           | =http://localhost:8080=              | the backend's own base IRI          |
| =AP_HANDLE=           | =pay3flow=                           | backend actor handle                |
| =AP_KEY_PATH=         | =./data/ap-key.pem=                  | RSA key used for signing            |
| =AP_REQUIRE_SIGNATURES= | =false=                            | verify inbound signatures or not    |

Also in =service/mod.rs=: =marketplace_resource = {AP_ORIGIN}/marketplace/resources/acquiring=,
=origin = AP_ORIGIN=.

* Where the request is triggered

- =GET /ws/rates= -- WebSocket: each message ={"type":"quote","request":{...}}=
  -> =quotes::compute_quote= (backend/src/server/routing/rates.rs);
- =POST /api/debug/quote= -- JSON =PaymentRequest= -> =compute_quote= (same file);
- =POST /api/debug/task= -- raw =command= and =content=, sent directly through
  =submit_request= (backend/src/server/routing/activitypub/mod.rs);
- =POST /payments/*= -- payment execution: reuses the same live-quote pipeline
  (fmatch -> fallback), see =payments/service.rs:146=.

All paths converge in =Service::submit_request("candidates", content)=
(=activitypub/service.rs:70=).

* Request parameters in =content=

The payment request (backend/src/routing/request.rs) has these fields:

| Field        | Type | Meaning                            | Example         |
|--------------+------+------------------------------------+-----------------|
| =amount=     | f64  | amount                             | =100.0=         |
| =currency=   | str  | currency code                      | =USD=, =EUR=    |
| =from=       | str  | source (channel/provider)          | =PayPal=        |
| =to=         | str  | destination (channel/provider)     | =VISA=, =Bank=  |
| =to_geo=     | ?str | destination territory (optional)   | =NL=            |
| =method=     | ?str | payment method (optional)          | =SEPA=          |

=quotes::fmatch_content= (=quotes/mod.rs:30=) renders them into a string:

#+begin_src text
transfer {amount} {currency} from {from} to {to};
currency={currency}; from={from}; to={to}[; to_geo={to_geo}][; method={method}]
#+end_src

Example: =transfer 250.5 USD from PayPal to Bank; currency=USD; from=PayPal;
to=Bank; to_geo=NL; method=SEPA=

fmatch reads this exact string to filter its pool of solvers (acquirers).

* Activity body (JSON-LD, fep/0837)

=request_proposal()= (activitypub/model.rs:118) builds:

#+begin_src json
{
  "@context": [
    "https://www.w3.org/ns/activitystreams",
    "https://w3id.org/fep/0837"
  ],
  "id": "{AP_ORIGIN}/requests/{uuid4}",
  "type": "Proposal",
  "purpose": "request",
  "attributedTo": "{AP_ORIGIN}/actor/{AP_HANDLE}",
  "name": "pay3flow request: candidates",
  "content": "transfer 100 USD from PayPal to VISA of BelarusBank; currency=USD; from=paypal; to=visa-belarusbank",
  "command": "candidates",
  "resultInbox": "{AP_ORIGIN}/inbox",
  "publishes": {
    "id": "{AP_ORIGIN}/requests/{uuid4}#intent",
    "type": "Intent",
    "action": "deliverService",
    "resourceConformsTo": "{AP_ORIGIN}/marketplace/resources/acquiring",
    "resourceQuantity": { "hasUnit": "one", "hasNumericalValue": "1" }
  },
  "to": ["https://www.w3.org/ns/activitystreams#Public"]
}
#+end_src

Fields that matter to fmatch:
- =command= -- request type; the backend always sends =candidates=
  (discovery-only: list only, no execution). fmatch's accepted values:
  =new=, =candidates=, =findbestpath=, =candidate= (discovery), =plan=,
  =accept=, =cancel=, =execute=;
- =resultInbox= -- where fmatch delivers the async result (for discovery
  commands the answer comes back inline; resultInbox is used for callbacks on
  real execution);
- =publishes.resourceConformsTo= -- the resource contract (acquiring);
- =content= -- the payment parameters from the section above.

* HTTP delivery (activitypub/delivery.rs)

Target: =POST {FMATCH_INBOX}=, header =Content-Type: application/activity+json=.

Every outbound activity is signed with an HTTP Signature (rsa-sha256, PKCS#1
v1.5, key from =AP_KEY_PATH=):

#+begin_src text
Host: localhost:7277
Date: Thu, 17 Sep 2026 12:00:00 GMT
Digest: SHA-256={base64(sha256(body))}
Signature: keyId="{AP_ORIGIN}/actor/{AP_HANDLE}#main-key",
           algorithm="rsa-sha256",
           headers="(request-target) host date digest",
           signature="{base64}"

Signing string:
(request-target): post /inbox/actra
host: localhost:7277
date: Thu, 17 Sep 2026 12:00:00 GMT
digest: SHA-256={base64(sha256(body))}
#+end_src

Delivery parameters:
- per-attempt timeout: 15 seconds;
- retries: up to 3, backoff =500ms * 2^attempt= (500/1000/2000 ms);
- retried: network errors, HTTP 429 and >=500; 4xx is not retried;
- idempotency: before sending, the =activitypub_deliveries(activity_id, target)=
  table is checked; re-sending the same =id= to the same inbox returns
  =AlreadyDelivered= without an HTTP request.

Any 2xx counts as success; the response JSON body is captured only in
=deliver_with_response= mode -- that is how the backend receives fmatch's
inline answer.

* Parsing the fmatch response

=AcquirerCandidate::from_reply()= (activitypub/model.rs:204) looks for
candidates in two places:
1. the top-level =candidates= array;
2. otherwise in =object.candidates= (an =Offer(Agreement)= reply with
   candidates).

Candidate fields (activitypub/model.rs:186):

| JSON field | Rust field      | Meaning                     |
|------------+----------------+-----------------------------|
| =name=     | =name=         | acquirer name               |
| =shortId=  | =short_id=     | short id (for =execute=)    |
| =rank=     | =rank=         | position (1 = best)         |
| =price=    | =price=?f64=   | effective price/commission  |
| =quality=  | =quality=?f64= | quality (0..1)              |

The result is folded into a =Quote= (=quotes/mod.rs:13=):
- =request= -- the original =PaymentRequest=;
- =source= -- =fmatch= or =fallback= (see routing/matcher.rs:RouteSource);
- =candidates= -- the ranked list;
- =best= -- the candidate with the minimal =rank=;
- =quoted_at= -- RFC3339.

=RoutePicker.resolve= (=routing/matcher.rs:101=): if the fmatch reply arrived,
the list is taken as-is (even when empty: fmatch is the source of truth); if
fmatch is unreachable, the local rules matcher (fallback) kicks in.

* What fmatch does with the request (brief)

- validates the FEP-0837 Proposal (=purpose=request=): checks =@context=,
  =id=, =publishes=, etc.;
- for =purpose=request= it checks =resourceConformsTo= and the subscription;
- the =candidates= command is recognized as *discovery-only*: no execution is
  created; fmatch returns an inline page of ranked =candidate_summaries= (the
  =candidates= field) with =mode="findBestPath"= and
  =detail="candidate list generated without candidate execution"=
  (fmatch/src/routing/entry.rs:693);
- for non-discovery commands (=plan=, =accept=, =execute=...) fmatch delivers
  tickets to candidates and sends the result back to =resultInbox=.
