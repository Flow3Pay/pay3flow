# План: быстрый поиск маршрутов и репутация провайдеров

**Статус: требования к будущей реализации.** Это описание пожеланий к Pay3Flow и
Fmatch, а не документация работающего поведения. Изменения поиска и репутации,
сделанные 3 октября 2026 года, были отменены; текущая базовая версия —
`20f9dfa`.

## Цель и обнаруженные проблемы

- Ускорить поиск обмена без изменения пользовательского сценария и состава
  поддерживаемых маршрутов. Маршруты должны появляться по мере готовности, а
  поиск — завершаться вскоре после того, как оставшиеся направления уже не
  могут дать результат.
- При обмене AMD → RUB и других фиатных направлений IDPay иногда появляется
  сразу, остальные маршруты — одной пачкой примерно через 6 секунд, а поиск
  заканчивается через 1–2 минуты даже для заведомо невозможных вариантов.
- Cardano (ADA) → AMD не возвращал маршруты, хотя BestChange показывал около
  60 подходящих предложений. BND → AMD тоже перестал находить маршруты,
  которые были доступны в старой версии. Эти направления должны войти в
  регрессионные проверки.
- Фоновый обход не должен перегружать CPU и память или мешать фронтенду:
  наблюдались 3,2–5 ГБ памяти, высокая загрузка CPU и `Failed to fetch`.

## Поиск и фоновые снимки

1. Вызовы Fmatch, которые сейчас запускаются пользовательским поиском для
   обменников, перенести в фон. Пользовательский запрос читает готовые снимки,
   строит маршруты из готовых коэффициентов и получает постепенные обновления.
   Сохранение полученных метрик и снимков выполнять асинхронно, не задерживая
   ответ клиенту.
2. Для обменников, не относящихся к P2P, обходить **все возможные комбинации**
   поддерживаемых валют, активов, сетей и направлений. Ориентир обновления —
   каждые 5 минут. Если полный проход дольше, продолжать ограниченный обход без
   запуска перекрывающихся волн задач. Поддержка редкого направления не должна
   зависеть от того, искал ли его пользователь ранее.
3. P2P искать по запросу пользователя, поскольку такой поиск сравнительно
   быстрый. Популярные P2P-направления дополнительно обновлять в фоне с
   интервалом от 15 секунд до 1 минуты. Точный алгоритм выбора интервала
   пользователь намерен определить отдельно.
4. Первый фоновый проход начинать сразу при запуске приложения. Последующие
   сроки обновления отсчитывать от него или от последнего успешного опроса
   соответствующего направления.
5. Сначала опрашивать часто запрашиваемые пары и провайдеров с более высоким
   приоритетом поиска, затем остальные. Репутация влияет на **очередность
   фонового опроса**, а не служит глобальным фильтром пользовательской выдачи.
6. Ограничить одновременно активные фоновые пайплайны максимумом в 50.
   Фактический лимит и паузы должны учитывать нагрузку на CPU и память, оставляя
   ресурсы для API и фронтенда. Очередь должна оставаться ограниченной по памяти
   даже при полном каталоге направлений; срочный запрос не должен ждать конца
   большого планового прохода.
7. Если снимок ещё не готов, запрос должен завершаться за ограниченное время
   понятным состоянием ожидания, а интерфейс — получить результат после его
   появления. Нельзя держать соединение в ожидании всего фонового цикла или
   навсегда оставлять форму в состоянии `Failed to fetch` после временного сбоя.
8. Кеш завершённых найденных маршрутов в общем Redis увеличить с 5 до
   **15 секунд**. Он должен переиспользоваться между пользователями для
   одинакового нормализованного запроса, без привязки маршрута к личности.

## Репутация и взаимодействия

Репутация ведётся для каждого P2P-провайдера и обменника. Активность маршрута
влияет на провайдеров, входящих в этот маршрут. Начальное значение — **50
баллов**, верхняя граница — **100 баллов**:

| Событие | Изменение |
| --- | ---: |
| Лайк | +10 |
| Дизлайк | −15 |
| Открытие инструкции | +5 |
| Переход по ссылке из инструкции | +5 |
| День без взаимодействий | −15 |

- Реализовать отдельные эндпоинты для открытия инструкции и перехода по ссылке
  из неё. Сервис остаётся максимально анонимным: идентификатор
  пользователя передаётся в теле события только для защиты от накрутки;
  публичные метрики и маршруты не привязаны к пользователю.
- Новые события сначала учитывать в Redis. Перед истечением срока жизни
  накопленных данных переносить корректные изменения в основную БД. Для
  каждого анонимного идентификатора/сессии сохранять состояние счётчиков до
  первого события: при выявлении явного спама отменять **только** события этой
  сессии после сохранённого состояния, не сбрасывая общий счётчик до одного.
  Одинаковое правило действует для инструкции, внешней ссылки и голосов.
- Репутационные показатели и вычисленные коэффициенты пересчитывать в фоне.
  Обновлять общий кеш репутации в Redis, чтобы очередной фоновый поиск не
  обращался за ней к основной БД для каждого провайдера.
- Репутация определяет приоритет поиска. На порядок выдачи
  пользователю влияют только лайки и дизлайки, умеренно и лишь при близкой
  выгоде маршрутов. Выгодный маршрут нельзя сильно опустить только из-за
  репутации. Пока голосов слишком мало, сохранять обычный экономический
  порядок.
- Учитывать соотношение и объём голосов: при близкой комиссии маршрут с
  100 лайками и 4 дизлайками должен быть выше маршрута с 16 лайками и без
  дизлайков; при 100 лайках и 68 дизлайках — ниже второго. Точную формулу и
  порог достаточности голосов ещё предстоит определить.

## Критерии готовности

- Холодный и тёплый поиск AMD → RUB показывают маршруты постепенно; отсутствие
  дальнейших допустимых путей быстро завершает поиск.
- Cardano (ADA) → AMD и BND → AMD находят доступные предложения обменников,
  включая BestChange, если провайдер их действительно отдаёт.
- Фоновый обход покрывает весь поддерживаемый каталог, но сохраняет отзывчивость
  API и фронтенда при долгом полном проходе. Нет повторения пиков памяти в
  несколько гигабайт или устойчивой перегрузки CPU.
- Одинаковые поиски разных клиентов используют общий 15-секундный Redis-кеш.
  Результат и интерфейс сохраняют прежний смысл; основное заметное изменение —
  скорость.
- Голоса и переходы дают описанные баллы, антиспам откатывает только
  накрученные события, а фоновый поиск читает репутацию из Redis. Ранжирование
  соответствует примерам выше.
- Документацию API, фонового цикла, кеша и репутации обновить после реализации.

## Порядок работы

Вести реализацию в отдельных worktree для Pay3Flow и Fmatch
(`fmatch-pay3flow-routing`); менять Fmatch, только если этого потребует контракт.
Делать небольшие коммиты, чтобы сохранялась история откатов; пушить в `master`
после завершения всей работы. Проверки на проде разрешены, но публикация новой
версии — отдельный шаг.
